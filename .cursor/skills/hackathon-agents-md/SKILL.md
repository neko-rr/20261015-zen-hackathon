# ハッカソン用 AGENTS.md 作成

プロジェクトルートに `AGENTS.md` を置き、**チーム全員・複数 AI ツール**（Cursor, Claude Code, Copilot 等）が同じ前提で動けるようにする。

## トリガー

- 「AGENTS.md を作成」「エージェント用の指示書を書いて」
- ハッカソン開始前のチーム共有セットアップ
- 技術スタック決定後の AGENTS.md 更新

## AGENTS.md とは

| 項目 | 内容 |
|------|------|
| 形式 | プレーン Markdown（**YAML frontmatter なし**） |
| 配置 | プロジェクトルート `AGENTS.md` のみ |
| 目的 | 推測できない情報（コマンド、構成、制約）を AI に伝える |
| 長さ | **150行以内**を目標。短いほど読まれる |
| 共有 | Git でチーム共有。秘匿情報は書かない |

### AGENTS.md vs `.cursor/rules`

| 用途 | 推奨 |
|------|------|
| ハッカソン全体の方針・チーム運用 | **AGENTS.md** |
| ファイル種別ごとの詳細ルール | `.cursor/rules/*.mdc` |
| 複数 AI ツールで共通の指示 | **AGENTS.md** |

ハッカソンでは **AGENTS.md を主**とし、必要になったら `.cursor/rules` を追加する。

## ワークフロー

```
Task Progress:
- [ ] Step 1: プロジェクト情報の収集
- [ ] Step 2: 不足情報の確認
- [ ] Step 3: AGENTS.md の作成・更新
- [ ] Step 4: 品質チェック
```

### Step 1: プロジェクト情報の収集

優先順位で読み取る:

1. `docs/*-regulation-summary.md` — レギュレーション要約（**`verified: true` または `primary_source` ありのみ信頼**）
2. `docs/*-summary.md` — 大会要約
3. `docs/tasks.md` — 参加ブロック・当日スケジュール
4. `docs/ideas/comparison.md` — 比較表・議論（確定前）
5. `docs/idea.md` — **採用アイデア**（決定後）
5. `README.md` — プロジェクト概要

**レギュレーション要約が未検証の場合:**

- `verified: false` または `primary_source` 無し → **応募要項 URL を直接確認**してから AGENTS.md に反映
- [hackathon-summary/verification.md](../hackathon-summary/verification.md) を参照

[hackathon-summary](../hackathon-summary/SKILL.md) で作成済みの `docs/` があれば必ず参照する。

### Step 2: 不足情報の確認

以下が未確定ならユーザーに確認する（推測で埋めない）:

- 技術スタック（言語・FW・デプロイ先）
- チーム役割分担（2名の担当）
- 当日の参加ブロック・提出期限

**スタック未確定**の場合: テンプレートの `{プレースホルダ}` を残し、「当日オリエ後に更新」と明記する。

### Step 3: AGENTS.md の作成・更新

[template.md](template.md) に従い、プロジェクトルートに `AGENTS.md` を出力する。

#### 記載ルール

1. **命令形・箇条書き** — 説明文より「やること／やらないこと」
2. **具体コマンド** — `npm run dev` 等、コピペ可能な形で
3. **ハッカソン制約を最優先** — 時間・MVP・レギュレーション
4. **docs/ へのリンク** — 詳細は要約ファイルに委譲し AGENTS.md は短く保つ
5. **既存 AGENTS.md がある場合** — 上書き前に変更点をユーザーに示す

#### ハッカソン向け必須セクション

| セクション | 内容 |
|-----------|------|
| プロジェクト概要 | 何を作るか、大会名、開発時間 |
| ハッカソン制約 | レギュレーションから逆算した制約 |
| チーム運用 | 役割、意思決定、コミュニケーション |
| ディレクトリ構成 | どこに何を置くか |
| 技術スタック | 採用技術と選定理由（短く） |
| コマンド | セットアップ・開発・デプロイ |
| 開発方針 | MVP優先、エージェントの判断基準 |
| 境界・禁止事項 | 秘密情報、過剰実装、触らないファイル |

### Step 4: 品質チェック

- [ ] 150行以内（超える場合は docs/ に移してリンク）
- [ ] APIキー・個人連絡先・参加URL が含まれていない
- [ ] コマンドがプロジェクトと一致（未確定なら `{TODO}` 明示）
- [ ] **審査・提出ルールが regulation-summary の `primary_source` と一致**
- [ ] プレゼン要否・提出形式を決め打ちしていない（要約を確認済み）
- [ ] チームメンバーが読んで同じ理解になる

## レギュレーション反映の注意

AGENTS.md に書く前に、以下を要約から確認する（**推測禁止**）:

| 項目 | 確認 |
|------|------|
| 審査方式 | プレゼン登壇 vs 審査員操作 |
| 提出物 | URL / 資料 / Drive 等 |
| 作品形式 | Web / Chrome / ネイティブ等 |
| 当日時刻 | 参加ラウンドのタイムテーブル |

## ハッカソン固有の開発方針（デフォルト）

AGENTS.md に含める既定方針。**レギュレーション要約で上書き**される場合はそちらを優先。

```
- MVP優先: 審査方式に合わせた「見せ方」を最優先
- 3時間開発: 新規ライブラリ導入は最小限
- 動く作品 > 完璧な設計
- 審査が「操作型」→ デプロイURL・3分フローを AGENTS.md に明記
- 審査が「プレゼン型」→ その場合のみ台本・時間を明記
```

## 更新タイミング

| タイミング | 更新内容 |
|-----------|---------|
| スタック決定時 | 技術スタック・コマンド |
| テーマ告知後 | プロジェクト概要・MVPスコープ |
| 当日朝 | 提出期限・デモ手順 |
| 決勝進出後 | 発表時間（10分+Q&A）等 |
